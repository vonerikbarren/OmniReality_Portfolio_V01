# OmniStore V181 — design notes (location, all emojis, D3 views, OmniTalent panel, arbitrage guard)

## 1. Store location (X, Y, Z)
- Setting `anchor: [x, y, z]` in `utils/OmniStoreSettings.js` (per store id, same sanitize / migrate / event path as the colours). Default `[0, 3, -40]` (the old fixed position). Clamp: x and z to +-500, y to -200..300; NaN / non-numbers are rejected per axis (the old value stays); stored settings without `anchor` migrate to the default. `resetAnchor()`; exports `DEFAULT_ANCHOR`, `ANCHOR_RANGE`, `clampAxis`, `normalizeAnchor`.
- `OmniStoreScene.setAnchor(a)`: moves the shelf group (furniture, slots, dome are children, so they move together), re-aims an in-flight camera pose, and when the player is viewing the store translates the camera and the orbit target by the delta so the view does not jump. `placeAtCamera()` (event `omni:store-place-at-camera`) puts the store 30 units ahead of the camera at camera height. Layout poses are anchor-space (`utils/OmniStoreLayouts.js`) and are offset by the anchor when flying, so all four layouts work at any anchor.
- Checks: nothing else assumed the old anchor (grep for -40 / the constant); the dome (R 120, hidden when the camera is beyond 0.92 R) is a child of the group, so it follows. Origin objects live around [200, 50, 300]: with the largest clamp the store can overlap them (x 500 is the other way); a store near [200, 50, 300] intersects them. Nothing prevents that: the user asked for freedom, the panel says it moves the whole store.
- UI: Look tab > Location (X / Y / Z inputs, Reset location, Place at my camera, plain note). Dev panel dump includes the anchor.

## 2. All emojis
- Data: `data/OmniEmojiData.js` is generated by `tools/build-emoji-data.mjs` from the npm package `emojibase-data` (17.0.0; en, compact). No skin tones; fully-qualified emoji only; 1,914 emoji in 9 Unicode groups (the "component" group is dropped); 122,700 bytes (limit 250 KB). Regenerate: `npm i emojibase-data` in a scratch dir, then `node tools/build-emoji-data.mjs <path>/node_modules/emojibase-data data/OmniEmojiData.js`.
- Picker `ui/OmniEmojiPicker.js`: search by name or keyword across all groups, nine group tabs, recents in `omni:store-emoji-recent-v1` (max 24, wrapped in try / catch). Mounted from the catalog product form (button "All emojis…"); the 24 quick picks stay.
- Demo store `utils/OmniEmojiCatalog.js` (pure) builds a catalog `omni-store-catalog/1` with one product per emoji, 9 extra sections (one per group), sandbox prices spread over the seeded value types. The Catalog tab button "Load all-emoji demo store" runs it through the same validator and `importProducts` path (merge or replace; replace needs a second press) and `rememberUndo`, so Undo last import works. The sections ride in the store's `extraSections`; `buildSections(extra)` appends them after the built-in ones.
- Limits (with evidence): `LIMITS.products` 500 -> 3000 (the demo is 1,914; headroom for a user's own); `LIMITS.emoji` 16 -> 32 (ZWJ sequences with skin tones or hair are up to 11 code points / about 20 UTF-16 units; 32 is a ceiling, the data's longest is shorter); the AI prompt's product ask stays at 500 (`AI_PRODUCTS_MAX`), so `buildAiPrompt` only changed by the emoji length wording. Meshes: slots are pooled per page (`perPage` 6..60), so a 1,930-product store measured 121 meshes (37 visible) in real Chromium, the same as 16 products; paging is by section chip and arrows. Storage: the 1,930-product store is about 837 KB in `omni:store-v1`; localStorage is about 5 MB per origin; the one-step undo snapshot is only persisted when it is <= 1,000,000 characters, otherwise it is kept in memory for the session.
- Rendering: emoji are drawn into canvas textures as before. In the test browser (Chromium, software GL) the colour emoji font drew the common emoji; the newest Unicode 16 / 17 emoji measured a different width (32 vs 39.9), so they are NOT confirmed to render there. A device with an up to date emoji font is needed for the newest ones.

## 3. D3 views
- Pure builders `utils/OmniValueViews.js`: `balanceTree`, `exchangeTree`, `formsTree`, `sellTree` (hierarchies) and `exchangeGraph`, `formsGraph`, `sellGraph`, `treeGraph` (sankey nodes / links). Sizes are DISPLAY sizes (log of a type's own amount, or shares inside one type): different value types are never added.
- `ui/OmniValueCharts.js` `ValueChart`: sunburst, treemap, sankey drawn as SVG with a viewBox and `width: 100%` (responsive, no horizontal scroll), nodes are keyboard buttons (Tab, Enter, Space) with `<title>` and aria labels, a caption line, click -> `onSelect(key, node)`. Libraries load once with dynamic `import('d3')` / `import('d3-sankey')`; a failure shows a plain message (the wheel keeps working) and is not cached, so the next draw retries.
- d3 source: the existing importmap in `index.html` (jsDelivr `+esm`), now pinned `d3@7.9.0` and `d3-sankey@0.12.3` (V176 pinned d3@7 only). A browser with no CDN access gets the message above. Tests use local npm bundles.
- Exchange panel: switcher `Radial wheel | Sunburst | Treemap | Sankey` (persisted `omni:exchange-view-v1`). Level 0 draws the accepted forms; a click on a form calls `selectSpoke(index)`, the same call a wheel spoke makes. Levels 1-2: `#exchange-chart-slot` (id kept) draws the quote (offer, route, fees, remainder) with Sunburst / Treemap / Sankey; Wheel is not offered there.

## 4. OmniTalent panel (item 5, part 2)
- Finding: OmniTalent exists only in docs (`BACKEND_COMPONENTS_ONTOLOGY.md`, the build order). There is no OmniTalent class, event, store or panel in the code before V181. So `ui/OmniValuePanel.js` is a standalone panel with id `omnitalent`, title `⟐OmniTalent`, built so a future OmniTalent shell can host or wrap it. It extends `OmniSettingsPanelBase`, opens on `omni:nav-select '⟐OmniTalent'`, is registered in `main.js`, the Drawer and the ribbon (Realities > Value > Talent), and reuses the wallet row (`balanceRowHtml`) and the exchange events.
- Shows `balanceTree()` (you > tier > type) as Sunburst / Treemap / Sankey (persisted `omni:talent-view-v1`), a detail block for the picked type (balance row + conversion edges), the arbitrage line, buttons to the exchange and wallet. Not built: quality ticks on balances (a balance has no grade).

## 5. Arbitrage guard (`utils/OmniValueModel.js`)
- `findArbitrageLoops({maxLen=5, owners, ...})`: simple cycles over the visible conversion edges (up to 5 edges, each type once); a loop is a loop when the product of its rates is above 1 + 1e-9 (an exact 1 is not flagged). Each loop has edges, types, multiplier, gain %, `minStart`, `needsGrade`, a worked `probe` (start, end, net, stated remainders after step rounding) and a plain line: "These rates form a loop that makes value from nothing: ...". Result is capped (`ARBITRAGE.maxLoops`, a cycle budget) and carries `truncated` and `checked`; the registry is cached by an edge signature. It never throws; a garbage edge is skipped.
- Guard: `quote()` returns `arbitrage {loops, chain, chainLine}`. Every route that uses a loop edge is WARNED. An exchange is BLOCKED (`canExecute` false, `block: 'arbitrage-loop'`, `buy()` error `arbitrage-loop`) only when the route adds an edge of a gaining loop while another edge of the same loop was used by this account's `buy` in the last `ARBITRAGE.chainMs` (10 minutes). The first leg is allowed (it may just be a normal trade); closing the loop is what is refused. Warnings show in the exchange panel, the OmniTalent panel and DevOmniStoreSettings (section e, "Rate loops", and the dump).
- Seed result: the seeded rates have NO gaining loop (checked on the default registry, and with the all-emoji demo, which does not change rates). Several loops multiply to exactly 1 (flowers > bells > credits > flowers), which is deliberately not flagged. Injected examples in the tests: credits > bells 4:1 against bells > credits 3:1 gives x1.333 (+33.3 %); adding the seeded bells > gold > credits path gives a second, longer loop.
